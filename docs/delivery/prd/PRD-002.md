# PRD-002 — Wallpaper Cache Invalidation

## Problem

Users installing the compiled executable of the Pegasus application experience an issue where the background wallpaper does not update correctly when applying a theme. While the theme's colors are applied properly, the wallpaper remains stuck on a previously cached version. This issue occurs in the packaged application (where file metadata like modification times might remain static), while the local development environment works correctly. 

## Objective

Ensure that whenever a theme is applied, the exact, most up-to-date wallpaper asset from that theme is correctly loaded and applied to the desktop. The system must reliably bypass any OS or application-level caching of older images, ensuring the desktop always reflects the true wallpaper asset of the selected theme.

## Target Users

### End Users

Users installing the application, applying updates, or installing custom themes. They expect their desktop background to seamlessly and accurately update to match their chosen theme without seeing outdated images.

## User Stories

### US-001 — Accurate Wallpaper Application

As an end user,
I want the correct background wallpaper to be applied when I select a theme in the installed application,
so that my desktop visually matches the chosen theme perfectly and doesn't display an old background.

Traceability:
REQ-001

## Functional Requirements

### FR-001 — Content-Based Wallpaper Identification

The system must uniquely identify wallpaper files based on their actual content (e.g., generating a unique hash) rather than relying on potentially static metadata like timestamps or file sizes.

Traceability:
REQ-001

### FR-002 — Cache Bypass

The system must ensure that the generated wallpaper filename or URI is unique whenever the image content changes, forcing the desktop environment to load the new image instead of a cached version.

Traceability:
REQ-001

### FR-003 — Universal Application

The new wallpaper caching mechanism must apply to all themes, including both built-in (packaged) themes and custom user themes.

Traceability:
REQ-001

## Non-Functional Requirements

### NFR-001 — Performance and Responsiveness

The process of generating the unique identifier (e.g., hashing) for the wallpaper must be highly performant. It must not freeze, block, or significantly delay the user interface during the theme application process.

Traceability:
REQ-002

## Business Rules

### BR-001 — Wallpaper Update Condition

A wallpaper must be considered changed and require a new cache entry if and only if its file content has changed.

Traceability:
REQ-001

## Constraints

### CON-001 — Packaged Environment Compatibility

The solution must work reliably within the Electron packaged environment, where files may be read directly from an `.asar` archive and metadata may not behave the same as a standard filesystem.

### CON-002 — GNOME Integration

The solution must remain compatible with the existing GNOME `gsettings` wallpaper application mechanism.

## Acceptance Criteria

- [ ] When a new version of a packaged theme is installed containing a modified wallpaper, applying the theme correctly sets the new wallpaper on the desktop.
- [ ] When a custom theme's wallpaper is modified by the user, applying the theme correctly sets the new wallpaper.
- [ ] The user interface does not freeze or exhibit noticeable lag while processing and applying the wallpaper.
- [ ] The desktop environment does not display outdated wallpaper images after a theme's wallpaper asset has been updated.

## Out of Scope

- Support for handling different wallpapers per monitor.
- Support for desktop environments other than GNOME.
- Image format conversion or compression of the wallpaper assets.

## Risks

- Hashing very large image files could potentially impact performance or block the Node.js event loop if performed synchronously.

## Assumptions

- The GNOME wallpaper daemon will successfully reload and display the image if the provided file path/URI is uniquely different from the previously applied one.
